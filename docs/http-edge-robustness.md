# The HTTP edge — what it admits, what it bounds, and what it answers

> **Status: design.** Written after a refutation review of the campaign plan measured every claim
> against the shipped vertx-core and vertx-web 5.1.6 jars and against this tree. Nine of the
> plan's positions did not survive that measurement and are replaced below, each with the
> measurement that replaced it. One slice had already shipped as #1149 and is reduced to its
> residue; two slices the plan did not contain were added, one of them a live bypass of the bound
> the campaign spends its length refining.

The edge this framework owns is small — a Vert.x server, a router, a body handler and an
admission gate — and almost every number inside it arrived by inheritance rather than by
decision. That is the defect class `HttpEdgeBeans` already names out loud about the body limit:
"the transport upgrade to Vert.x 5 changed that default from unlimited to 10 MB, silently — a
borrowed bound nothing declared." This document takes the rest of that inventory: which bounds
the edge admits requests under, which ones it decodes bodies under, how long it will hold a
connection that has stopped making progress, and what a caller is told when one of them refuses.

Six findings from the 2026-09-04 audit sit underneath it (F34, F35, F36, F37, F38, F39). Two more
subjects are here because the review found them while measuring those six: the admission gate
compares a path the router does not route on, and a capacity refusal hands a browser a JSON
document to paint.

## What is true today

**One budget admits everything, and a dot segment walks past it.** `HttpAdmission` holds
`tesseraql.http.maxInFlight` permits — `workerThreads x 4`, forty by default — and exempts the
health and asset mounts. It compares `ctx.request().path()`, the target as transmitted, while
vertx-web matches routes on `ctx.normalizedPath()`. Reproduced over a raw socket against 5.1.6:
`GET /_tesseraql/health/../../api/orders` is exempted by the gate and then answered 200 by the
business route.

**An event stream stands in that budget for fifteen minutes.** An SSE connection is neither
health nor an asset, so it takes a request permit at `admit` and returns it only when the routing
context ends. Under `tesseraql host` the same connection has already taken one of ten per-member
forwarding permits at the front door, which is the bound that binds first: roughly three
signed-in users saturate a member's whole share while the member itself is idle.

**Three form-decoding bounds are Vert.x's.** 8192 bytes per attribute, 256 fields, 1024 buffered
bytes. A 5 MB textarea is refused with a bare `HTTP/1.1 400` whose body is
`java.io.IOException: Size exceed allowed maximum capacity`, while `tesseraql.http.maxBodyBytes`
— the bound the framework publishes for exactly these bytes — never gets to speak. The largest
form this framework renders is not a list page but the IAM admin user directory, which posts one
checkbox per row of `tql_users` and breaks at 255 users today.

**A router-level 400 has no code, no sentence and no fragment.** `HttpBodyLimit` owns the 413 and
is the only `errorHandler(` in the product. Every decoder refusal falls to vertx-web's default:
the reason phrase as the body, and `Unhandled exception in router` with a stack trace per attempt.

**A peer that stops reading holds a thread, a permit and a socket indefinitely.** Both write
loops wait on a bare `written.get()` with no deadline, and the admission permit is released only
from the routing context's end handler. Forty stalled sockets close the runtime to everyone else.

**Two caller faults are reported as server faults.** A `?page=` the arithmetic cannot hold and a
malformed JSON body at any of eleven authentication endpoints are both answered 500, with a
logged stack trace, against contracts that promise a field-scoped 400.

**A capacity refusal is a JSON document.** The gate and the relay both write an envelope straight
to the wire, so a browser navigating to a busy runtime paints
`{"error":{"code":"TQL-RATE-4293",…}}` as the whole page.


## Decision 1 — The gate keys on the path the router matched

**What is true today.** `HttpAdmission.admit` reads the raw request line — `String path = ctx.request().path()` (HttpAdmission.java:74) — and exempts two prefixes from the in-flight permit: the health mount and the asset mount (HttpAdmission.java:75, from the values built at :51-54). vertx-web does not route on that string. It matches on `ctx.normalizedPath()`, which decodes unreserved percent-escapes and removes dot segments. The two keys diverge, and the divergence is a live bypass of the whole bound, reproduced end to end against the shipped vertx-core/vertx-web 5.1.6 over a raw socket so that no client could normalize on our behalf: `GET /_tesseraql/health/../../api/orders` is exempted by the gate and then handed to the business route with a 200, and `GET /assets/../api/orders` does the same through the asset exemption. `GET /_tesseraql/%65vents` reaches the SSE mount while the gate sees the undecoded spelling.

**What changes.** All three membership tests in `admit` — the health prefix, the asset prefix, and every mount set a later decision adds — are compared against `ctx.normalizedPath()`. Nothing else moves: the permit, the release from the end handler (HttpAdmission.java:86) and the refusal (`TQL-RATE-4293`, :96-105) are untouched.

**Why this is a precondition and not a tidy-up.** Every subsequent decision in this document spends its length refining a bound that a dot segment walks past, and decision 2 adds a second budget selected by exactly this comparison. A stream budget written against the raw path is opt-out-able by spelling: the caller picks which budget to land in. The repair therefore precedes the budget rather than being retrofitted into it.

One lead was chased and rejected rather than carried as a caveat. A rerouted request does not take two permits. `UnicodePaths.install` registers at TesseraqlRuntime.java:1895 and `HttpAdmission.install` at :1899, both at `Integer.MIN_VALUE` with registration order preserved, and vertx-web nulls `normalizedPath` before `restart()`, so the gate runs once, on the decoded path. A comment at the install site records that this ordering is load-bearing.

**Accepted cost.** The asset carve-out becomes narrower: it now covers only the paths the router itself treats as assets. That carve-out is a recorded decision (docs/http-threading.md:289) — a stalled asset download holds a virtual thread and a connection under no permit at all — and this decision narrows it without reopening it.

## Decision 2 — Event streams take their own admission budget, not an exemption

**What is true today.** One semaphore admits everything. `HttpAdmission` holds `tesseraql.http.maxInFlight` permits — `workerThreads x 4`, forty by default (TesseraqlRuntime.java:336-341) — and exempts only the health and asset mounts (HttpAdmission.java:75). An SSE connection is neither. It takes a request permit at `admit` and returns it only when the routing context ends (HttpAdmission.java:79, :86), which for `/_tesseraql/events` is up to fifteen minutes later (LiveEvents.java:28-29). A handful of open live pages stand permanently in the budget ordinary routes are refused from.

**What changes.** The SSE mounts get their own semaphore, `tesseraql.http.maxEventStreams`, taken by those mounts and by nothing else, compared on the normalized path decision 1 established. Beyond it the answer is 503 with `Retry-After` and `TQL-RATE-4295`, written on the event loop before a virtual thread is spawned or a session row is read. `SseRoutes.register` (SseRoutes.java:75-82) records each mount it creates into the set; both SSE mounts already funnel through it, and there is no third (`LiveEvents.java:38` and `CopilotRoutes.java:98` are the only call sites in the tree).

**The reason first written down was false, and is replaced.** The campaign argued that an exemption would be an unbounded door for an anonymous caller. It would not. `BrowserAuthenticator` refuses an unauthenticated connection before the stream opens (SseRoutes.java:95-105 into the refusal render at :126-147). It also argued that many authenticated subjects could push the stream count arbitrarily high — 256 x 4. That arithmetic is impossible: `LiveStreams.total` is a single global counter across every subject (LiveStreams.java:68), incremented at :145, decremented at :180, and refused at `total >= maxTotal` (:133-138); the per-subject path at :126-130 evicts the subject's own oldest stream rather than adding one.

**The true reason is that an exemption removes the bound on connection *attempts*.** Every attempt spawns a virtual thread (SseRoutes.java:93) and reads the session store before `handler.begin` runs, and therefore before the registry can refuse it. That store is JDBC by default and borrows from the framework datasource, whose default pool is ten; the session is re-read on every frame, including each 25-second heartbeat (SseRoutes.java:196). Unbounded attempts against that pool are exactly the coupling the admission gate exists to prevent. One SSE mount also has no registry cap of any kind: the Studio copilot stream registers straight on `SseRoutes` and never subscribes (CopilotRoutes.java:96-98).

**The number is its own, not derived from the live registry.** The campaign proposed defaulting `maxEventStreams` to `tesseraql.live.maxTotal` (256) and claimed it would finally make `TQL-RATE-5030` reachable. That is backwards three ways. The registry is constructed only when an inbox channel is configured or some route declares `emit:` (TesseraqlRuntime.java:1087-1094), so in a portal or copilot-only runtime the key governs nothing present, and no bundled app declares `emit:` at all. Its value is parsed with a bare `Integer::parseInt` (:1089-1093) unlike every `http.*` count, so deriving the default would turn a today-inert typo into a boot failure carrying `NumberFormatException` instead of the framework's own refusal. And an outer gate equal to the inner cap makes 5030 *less* reachable, not more, because the outer gate refuses the 257th stream first — worse, the copilot mount consumes an outer permit while consuming no registry slot, so any constant headroom is defeated by that many concurrent copilot connections. `tesseraql.http.maxEventStreams` therefore defaults to the same number `maxInFlight` does, read through the same positive-integer validation (`threadCount`, TesseraqlRuntime.java:374-396). That keeps today's effective stream ceiling exactly where it stands and changes only whose permits a stream consumes.

**Why a stream earns a budget where a download earns a stall bound.** A stream is idle by design; there is no progress to measure and no honest timeout to apply, so the only bound available is how many may stand open. A response body that has stopped being read is measurable, so decision 8 bounds it with an idle timeout rather than a second budget. The two treatments follow from whether progress can be observed.

**Accepted costs, said out loud.** Two numbers now answer "how many responses does this runtime hold at once" — forty requests plus forty streams on defaults, where docs/deployment.md:108-111 publishes one; the table row and its 503 paragraph are amended in the same edit, which is the price of letting a monitor tell a refused route from a refused stream. `TQL-RATE-5030` stays unreachable at defaults, and bending a socket budget to make its refusal fire would be paying a real cost for a documentation problem — docs/realtime.md:52-59 gains the condition under which the global cap is reachable instead. A subscription outlives its connection by up to one heartbeat, because the permit returns at HttpAdmission.java:86 while the registry slot is released only when the producer's next await returns; that no longer decides which gate refuses, and closing it is its own finding. The copilot mount shares this budget while having no inner cap of any kind; it is off by default and absent from the host dist, so one budget with the fact recorded is proportionate. And on both shipped shapes the member-side refusal is out of reach at defaults, because the gateway's ten per-member permits (StackRelay.java:253, :476-484) are exhausted first — which is why decision 3 ships in the same campaign. What the member-side budget buys immediately is isolation, not a new refusal: forwarded streams stop standing in the request budget.

This amends docs/http-threading.md decision 2's closing sentence, which said bounding SSE datasource contention was decision 3's job and not a second set of numbers. A fifteen-minute hold on a request permit is not the contention that sentence was describing, and the sentence is amended rather than quietly outlived.

## Decision 3 — The front door sizes a member's event streams apart from its requests

**What is true today.** The gateway takes one permit per forward, per member, and holds it until the forwarded response ends or the connection closes (StackRelay.java:476-484, released from the endHandler/closeHandler pair at :380-391). That is the whole of the containment docs/http-threading.md decision 5 records: a member whose database has stalled holds its own share of the front door and nothing else. An event stream is a forwarded response like any other, so it holds a permit for its whole life, and the relay cannot tell one from a request — the only request header it reads is `X-Tenant-Id` (StackRelay.java:167, read at :452). A member's stream mount is base-path-prefixed (SseRoutes.java:75-82), so it falls outside `insideTheOriginFence` (StackRelay.java:357-368) and reaches the permit.

The share is ten by default (StackRelay.java:253; MultiAppGateway.java:283-301). The plan claimed ten open tabs saturate it. That magnitude is wrong and is corrected: `LiveStreams` caps a subject at four (LiveStreams.java:39) and *evicts* rather than refuses (:126-130), and an eviction ends the response so the relay releases. With the shell's inbox bell and a live view region both subscribing under one subject, roughly three signed-in users saturate a member's entire front-door share, and every ordinary request to that member is then answered 503 with `TQL-RATE-4294` while the member itself is idle.

**What changes.** Streams get their own per-member share. `tesseraql.gateway.maxStreamsPerMember` defaults to `maxConcurrentPerMember x 4` — forty where nothing is declared, the same shape a runtime derives `maxInFlight` from `workerThreads`, and the same number a member's own gate admits. Beyond the share a stream forward is refused 503 with `Retry-After` and `TQL-RATE-4296`, written by the relay's own envelope writer beside 4294 (StackRelay.java:737-748).

**The default of 256 the plan proposed is rejected, and its stated reason is not implementable.** The gateway reads the stack file (MultiAppGateway.java:283-301) and cannot see a member's own manifest key, so "the member's own stream budget" is not a number the front door can know. Worse, a member admits forty in flight, so 216 of 256 stream forwards would be answered `TQL-RATE-4293` one hop later — the exact failure MultiAppGateway.java:276-281 records the existing number to prevent.

**The two hops classify a stream by the same fact: the normalized request path.** The relay already resolves the member that answers for a path, and therefore that member's declared base path (StackRelay.java:329-347), so it matches the framework's stream mounts under it — `<basePath>/_tesseraql/events` and the Studio copilot's `.../ui/copilot/stream` — the way the runtime's own gate matches its mount set. `Accept` is rejected as the discriminator, and the plan's claim that "neither budget can starve the other" is false. A member serves MCP over Streamable HTTP at `<basePath>/_tesseraql/mcp`, and the repository's own MCP client sends `Accept: application/json, text/event-stream` on synchronous tool calls that are not streams, so a header test bills the whole MCP surface to the stream share. And a header is the caller's to set: it would let a client choose which budget its slow requests spend, making the stream share starvable by non-streams — the direction that matters, because the half that starves is live updates.

**The transport is sized to both shares.** `outboundPool` carries the sum — fifty by default rather than ten — because on HTTP/1 one forward pins one pooled connection, and an admitted forward that queues in the client is the queue this design removed one hop earlier. docs/http-threading.md:212-219's invariant, "the outbound client is sized to the same number", becomes "sized to the sum of the two shares, in both protocol modes", and `tesseraql.gateway.maxConcurrentPerMember` is published as bounding a member's non-stream forwards with the total stated beside it. One sizing rule for both protocol modes is kept deliberately: at a sum of fifty rather than the plan's 266, the simpler rule preserves the protocol-independence property that decision exists to hold.

**Accepted costs, said out loud.** The per-member ceiling rises from ten to fifty and read-idle is still off by default, so a hung member can hold five times as many forwards as today; containment is preserved in kind — still that member's own share and nothing else — and the alternative, reserving streams inside the existing ten, leaves a member with three live users no request capacity at all. Forwards inside the origin fence take no permit before or after this change (StackRelay.java:432-436 returns before the permit block), so a stream served by the stack surface runtime is unbounded at the front door; that is recorded as a known door rather than closed here. The gateway's share and a member's `tesseraql.live.*` caps stay independent numbers with independent derivations, and the front door's is deliberately the smaller. A saturated member becomes a browser reconnect loop: the bundled SSE extension retries on its own timer, never reads `Retry-After`, and its backoff is `Math.random() * (2 ^ retryCount) * 500` — XOR, so it is zero at one attempt and capped near 3.5 s; `Retry-After` on 4296 is justified as an API-client hint only. Finally, the relay matches the raw request URI (StackRelay.java:730-735) while a member's router matches the normalized path, so an encoded or dot-segmented spelling of a stream mount falls into the request share; the match normalizes, and the fail-safe direction — billing a stream to the smaller budget — is today's behaviour anyway.

## Decision 4 — The form decoder's per-field ceiling sits above the body limit, and only the attribute bound moves

**What is true today.** The runtime builds its server from a bare `HttpServerOptions` (TesseraqlHttpServer.java:87), so all three of Vert.x's form-decoding defaults are in force: 8192 bytes per attribute, 256 fields, 1024 bytes of undecoded remainder. The first is the defect. A 5 MB textarea is refused with a bare `HTTP/1.1 400` whose body is `java.io.IOException: Size exceed allowed maximum capacity`, while `tesseraql.http.maxBodyBytes` — the bound the framework publishes for exactly these bytes, 10 MB by default (docs/deployment.md:118) — never gets to speak.

**Raising the ceiling to the body limit does not fix it.** The transport offers every chunk to the decoder before the body handler counts it, so two bounds set to the same number are a race the decoder wins: measured, with both per-field bounds set exactly to the body limit, an over-limit chunked body answered 400 where the same body answered 413 once the bounds sat above it. The two refusals are not interchangeable. The 413 drains the rest of the upload so the answer can arrive, a discipline `HttpBodyLimit` exists to keep; the decoder's 400 drains nothing.

**What changes.** The attribute ceiling is set one transport delivery above the body limit, and nothing else moves. `setMaxFormAttributeSize((int) Math.min(maxBodyBytes + 65_536L, Integer.MAX_VALUE))` when `maxBodyBytes >= 0`, and a declared 10 MB when the body limit is opted out with `-1`. An HTTP/1.1 chunk is capped at 8192 bytes and an h2 frame at 16 KB, so 64 KB of headroom guarantees the body handler's counter is crossed on a strictly earlier chunk and the 413 wins by construction. Measured against the jars on the runtime's own classpath: under a 1 MB limit a 500 KB field answers 200 where it answers 400 today, and a 4 MB field answers 413 — urlencoded and multipart alike.

**Two claims of the original decision were false and are struck.** First, the buffered bound is *not* a per-field size bound and does not have to move. The decoder drains the undecoded remainder into the attribute on every parse, so with only `maxFormAttributeSize` raised and the buffered bound left at 1024, a 5,000,000-byte field posted in 610 flushed 8 KB chunks returned 200 with the correct digest, in both encodings. The remainder grows only when nothing can be parsed at all — a field name with no `=`, a multipart header with no CRLF — which is the input the bound exists to refuse. The campaign's claim that leaving it would "leave the textarea broken on a real network" is measurably wrong.

Second, `-1` (unlimited) is rejected for both bounds. The buffered bound is the decoder's only self-termination: Vert.x destroys and nulls the decoder solely on the decoder's own exception, and a 413 does not stop it, so a request refused for size goes on being decoded for the whole drain. Measured: with the bounds finite, `answer=413, heapRetained=9 MB, decoder destroyed`; with them unlimited, `answer=413, heapRetained=71 MB, decoder alive, undecodedChunk readable=38,242,706`. And under the documented `tesseraql.http.maxBodyBytes: -1` opt-out `HttpBodyLimit` registers no 413 handler at all (HttpBodyLimit.java:55-62) and the body handler's counter is skipped: with both decoder bounds also off, a 100 MB post drew no answer whatever, against the 400 that deployment gets today. Opting the wire bound out delegates it to an edge proxy; it does not opt out the decoder's memory bound.

**Accepted costs, said out loud.** The form ceiling is now decoded on the event loop at the size of the whole body — up to `maxBodyBytes`, 10 MB by default — where today the decoder refuses past 256 x 8 KB. A urlencoded body is held three times at the end of a request: in the body handler's own buffer (the urlencoded exclusion is commented out upstream), in the decoder's memory attribute, and again as the `String` the decoder materialises. The worst-case form heap is therefore roughly `maxInFlight x maxBodyBytes x 3`, about 1.2 GB at the shipped defaults of forty and 10 MB, against an image that sets no heap flag. `maxBodyBytes` is the knob that sizes heap and event-loop time together, and a deployment raising it for large imports raises both. Where `maxBodyBytes` is declared at or above 2 GB the `Integer.MAX_VALUE` clamp puts the ceiling below the limit and an oversize single field answers the decoder's 400 again; that is the stated edge of the guarantee, and the clamp is what keeps every form failure inside the exception types the transport catches. A deployment that declares an unusual form shape — over 1 KB of input with no `=` and no `&`, or a multipart header line over 1 KB — is refused with 400 at 1 KB rather than decoded; no browser or bundled template produces that shape.

## Decision 5 — The form field count is the framework's, and it is a transport-safety bound

**What is true today.** The edge inherits Vert.x's `DEFAULT_MAX_FORM_FIELDS = 256`, because `TesseraqlHttpServer.start()` builds a bare `new HttpServerOptions()` (TesseraqlHttpServer.java:87). Netty refuses the 257th field before any route runs, and the router answers a body of literally `Bad Request` plus a stack trace per attempt.

The count is the one dimension `maxBodyBytes` cannot bound: a 10 MB urlencoded body of empty pairs is millions of Netty `Attribute` objects, and the decoder disables the bound only at `maxFields <= 0`. So the count earns a key: `tesseraql.http.maxFormFields`, read beside `maxBodyBytes` in the same reader shape (absent → the default, `-1` → the documented opt-out Vert.x honours and the escape hatch its neighbour in the deployment table already publishes). It is not read through `threadCount`, whose contract is `>= 1` and whose refusal is `BAD_THREAD_COUNT`.

**The plan's anchor is wrong twice, and both errors are recorded.** First, a list form does not post one field per membership row — it can post two. `tql/view/list.html` opens one form at :69 and closes it at :173; the membership hiddens (`name="keys"`, one per row, :78), the pager's submit buttons (:137-152) and the bulk action buttons (:96-98) all sit inside it, and `table.html:48-49` renders `name="ids"` once per rendered row wherever the view declares `actions:`. Select-all checks every rendered row. The worst case is `cap + min(size, cap) + chrome`, and the legal declaration `{strategy: snapshot, cap: 500, size: 500}` posts 1002 fields — over the plan's proposed 1000. `InputRules.java:105-115` bounds neither `cap` nor `size` from above, and the route schema gives both a minimum with no maximum.

Second, the largest per-row form this framework renders is not a list view at all. It is the IAM admin user directory: no `pagination:` block, no row cap passed to its contract binding, no LIMIT in `list-users.sql`, and a bulk form posting one `ids` per row of `tql_users` plus `_csrf` and `action` (iam-admin `users/list.html`:69-97). It breaks at 255 users today and would break at 999 under a 1000-field bound. No finite transport number covers an unbounded grid. It is paged like every other list (slice 12), which is the maintainer's call between paging it and capping it: a directory is the one admin surface that grows without bound, so the single grid was always going to run out, and a cap would have refused above its ceiling where a pager keeps every user reachable.

**What changes.** `tesseraql.http.maxFormFields` defaults to **10,000**, recorded for what it is: the count above which a form body is treated as hostile, not a model of any page. That is roughly nineteen times the shipped worst-case page of about 525 fields, and some two orders of magnitude below the ~3.5 million attributes an unbounded count would admit inside the 10 MB body bound. It is an anonymous-body allocation bound applied runtime-wide — the same decoder serves the sign-in form — so it belongs to the operator and to nothing else.

**The route-scoped answer stays the only refusal an honest page may meet.** A posted membership above `pagination.cap` is refused with `TQL-FIELD-4222` at 422, naming the cap and telling the user to narrow (PageBinder.java:127-131). The transport count exists so an anonymous body cannot allocate unboundedly; the route cap exists so a search cannot freeze an unusable membership; a deployment in which the transport count fires first is misconfigured.

**Three mechanisms were considered and are deliberately not used.** A derived default cannot be computed where the edge settings are built: `HttpEdgeSettings` is constructed at TesseraqlRuntime.java:1251-1254, before the main app's routes compile at :1256 and before mounted apps load at :1262, so a maximum taken over route data would be blind to the bundled surfaces — and route YAML must not raise a decoder bound that guards every endpoint, sign-in included. A lint rule cannot read the number it must compare against: `LintContext`'s constructor takes an app home, findings, catalog tables and expression functions (LintContext.java:45) with no `AppConfig` and no accessor for one, `AppLinter` never runs at boot, and an operator's value is frequently an `${env}` placeholder resolved on the deploy host. And a boot-time or route-compiler refusal is disproportionate: under `tesseraql host` one member's boot refusal shuts down every member already serving, a whole-stack outage in place of one degraded page.

What holds the relationship instead is one build-time assertion, sited in tesseraql-runtime beside the edge defaults where both numbers are visible and no container is needed: the shipped `maxFormFields` default must exceed `PageSpec.effectiveCap() + effectiveSize() + CHROME_HEADROOM`. The guarded quantity is the form's whole field budget, not `cap` alone, because `cap:` is illegal on an offset route while `page: size:` has no upper bound at all, and an offset list declaring a large page size with `actions:` breaks identically. Move either number and the build goes red.

**Two facts make the generous fixed number sufficient rather than merely convenient.** A cap is meaningful only up to `tesseraql.resultMaterialization.maxRows` (default 10,000); a larger cap is already refused at execution with `TQL-LD-0001`. And the same bound covers the second surface that renders one hidden input per item — the edit-conflict dialog's replay of the original submission, which posts to the action route and declares no `pagination:` of its own.

Widening also repairs a shipped surface the campaign never counted: Studio's decision-table grid posts `2 + 2C + C(R+1)` fields, which at its own declared maximum of twelve columns and nineteen rows is 266 before a single delete box is checked. The largest legal decision table cannot be saved on main today.

**Accepted costs, said out loud.** An operator who lowers the key below an application's page budget still gets a refusal on one list page with no earlier warning; the only enforcement that could warn earlier is the boot refusal ruled out above. The build assertion guards the framework's own defaults, not an author's declaration: an author who raises both `resultMaterialization.maxRows` and a route's cap into five figures can still exceed 10,000 fields — that needs two deliberate raises and lands on a coded refusal. Two refusals still share one condition: below the count a caller meets `TQL-FIELD-4222` at 422, above it the transport's 400; the boundary is stated in the deployment-table paragraph. And the refusal a user sees for an over-budget POST remains a whole-page envelope, because the snapshot pager is a native submit — no `hx-*` attribute appears on `list.html`'s form, its pager buttons or its action buttons — so no fragment the page never swaps would help.

## Decision 6 — The router's 400 is typed, and it says which bound the body crossed

**What is true today.** The runtime owns exactly one router status. `HttpBodyLimit.install` registers `router.errorHandler(413, …)` (HttpBodyLimit.java:62) and it is the only `errorHandler(` in the product. Every other router-level 400 falls to vertx-web's default, which ends the response with the reason phrase — a body of literally `Bad Request` — and logs `Unhandled exception in router` with a stack trace. Form-decoder refusals land there: the body handler catches the decoder's exception and calls `context.fail(400, t)`. A caller who posts too many fields, an over-size attribute, or a body the decoder cannot read gets no code, no sentence and no fragment.

The fault is raised before any route context exists, so a router-level `errorHandler(400, …)` is the only place that can type it, and the 400 slot is free.

**Four shapes, named — not two.** `TooManyFormFieldsException` and `TooLongFormFieldException` arrive with a null message, because their only constructor is no-arg. The attribute bound arrives as a bare `java.io.IOException("Size exceed allowed maximum capacity")`, unwrapped by the body handler from a wrapper that carries a cause. And `ErrorDataDecoderException` arrives intact whenever the decoder built it from a message with no cause — a body containing `%zz` is the ordinary way to see it; it has a `(String)` constructor and so survives the cause-gated unwrap. Each branch names only what it knows. The field count names `tesseraql.http.maxFormFields`. The `IOException` names the attribute-size bound. `TooLongFormFieldException` says the decoder read past the buffered bound without finding a field delimiter; it does **not** mean the body was too large — the campaign recorded that bound as catching a value split across two network reads, and that is measurably wrong (a 200 KB value written in three chunks 150 ms apart decodes to 200 OK, while 5,000 bytes of field name with no `=` refuses). `ErrorDataDecoderException` names no bound at all, because none was crossed.

**The code is `TQL-FIELD-2012`, not a SEC code.** The plan proposed `TQL-SEC-4151`. SEC is the security namespace and its own recorded reasoning is that everything it does not enumerate is a server-side fault: its arm ends `default -> 500` (ErrorResponseRenderer.java:545). A caller-fault SEC code therefore drags a hand-written `case` in tesseraql-compiler into a runtime slice and lands inside `StatusMappingLedgerTest`'s 4000-4999 scope. FIELD ends `: 400` with no arm at all (ErrorResponseRenderer.java:552) and 2012 is free. It is also the right family on meaning: `TQL-FIELD-2002` already reads "Request body is not valid JSON", and this is its sibling for a form body. The consequence is that **this campaign makes no edit to `ErrorResponseRenderer` at all** — the renderer's collision on the ledger is removed rather than managed.

**Three properties the handler holds, because the failure can be absent.** A throw during route matching calls the unhandled-failure path directly rather than `fail()`, so the throwable is never stored. `GET /%zz` is the two-character reproducer: the handler runs with `ctx.failure()` null, `ctx.statusCode()` equal to `-1`, and `ctx.normalizedPath()` throwing the same `IllegalArgumentException` that caused the failure. So the handler hard-codes 400 and never reads `ctx.statusCode()`; it reads only `ctx.request().path()` and the `HX-Request` header, never `normalizedPath()`, `queryParams()` or `pathParams()`; and its whole body is wrapped, because a throw inside an error handler is swallowed as `Error in error handler` and the caller silently gets the reason phrase. It opens with `if (ctx.response().ended()) { return; }`, mirroring HttpBodyLimit.java:140-142, because a decoder limit can trip during the 413's drain.

**The unrecognised branch writes nothing, but logs.** There is no codeless envelope — `ErrorEnvelope.json` takes a `TqlErrorCode` and refuses a String overload on purpose (ErrorEnvelope.java:24-31) — so "a plain 400 envelope" would have to mint a second code or answer vertx-web's own 400s with the form's code. It does neither: for a failure it does not recognise the handler returns without touching the response and vertx-web finishes exactly as today. But it logs first, once, at WARN, with the request's raw path, its method and the failure's class. Registering any handler in the 400 slot takes the `else` branch away from vertx-web's own error log, so a malformed query string, a missing `Host` header and an empty path would otherwise lose their only server-side trace. This handler is the last thing that still sees them.

**The fragment serves the forms that post through htmx, and the pager is not one of them.** An `HX-Request: true` refusal answers with the `data-hc-field-errors` alert the swap allowance already reads, exactly as the 413 does (HttpBodyLimit.java:182-188). Four framework surfaces post through htmx — the declarative form, the import form, the import confirm and the job-card cancel. The snapshot pager is not: `list.html:69` is a bare `<form method="post">` whose pager buttons are native submits, so it never sends the header and takes the JSON branch. That is the published contract, not a gap, and the campaign stops claiming this decision closes a rendering regression on the snapshot pager.

**Accepted costs, said out loud.** Under decision 4's ceiling the fragment branch has no framework-generated consumer at defaults: a browser's `Content-Length` makes the body handler answer 413 before the decoder runs, and no generated form approaches 10,000 fields. The branch is kept deliberately — it is one ternary reusing the shipped 413 shape, it becomes live the moment an operator sets a form bound below `maxBodyBytes`, and a 400 that rendered nothing beside a 413 that renders an alert is the asymmetry this repository removes on sight. On the import surface the fragment is delivered into `hx-select=#<formId>-result` with `hx-swap=outerHTML` and a bare alert carries no such id, so htmx selects nothing; that is pre-existing — the 413 fragment has had exactly this shape on exactly this surface since it shipped — and it belongs upstream in Hypermedia Components or in the import template, never patched here. The native-POST surfaces receive the JSON envelope rendered as the whole document, which docs/hypermedia-ui.md already states. And registering the handler trades vertx-web's stack-trace ERROR for a one-line WARN on the unrecognised branch; that is the price of a typed body, so the line is mandatory.

## Decision 7 — An upload spools inside the application's declared work directory

**What already shipped, and what did not.** The move itself is on main as #1149. Vert.x resolves `BodyHandler`'s `file-uploads` default against the process working directory, and vertx-web creates that directory for every url-encoded form post, not only for multipart — so on the shipped image, whose `WORKDIR` is left root-owned while the process runs unprivileged, an ordinary sign-in form decided whether the runtime could answer. `HttpEdgeSettings` now carries the spool, `HttpEdgeBeans.newBodyHandler` sets it, and `TesseraqlHttpServer.start()` creates it at boot (TesseraqlHttpServer.java:84) before binding the body handler. Two things in that decision are not yet true, and this campaign carries them as a small follow-up.

**The path is not resolved through the relocation key.** `TesseraqlRuntime.java:570` writes `appHome.resolve("work/tmp/tesseraql")` by hand, while the same method calls `WorkHome.resolve(appHome, manifest.config())` at :1555. `WorkHome`'s own Javadoc states the invariant — the key is "honored everywhere or nowhere; a half-honored relocation key is exactly the emitted-but-dead class this closes" — and `tesseraql.app.work` is scaffolded into every application with `WorkHome` registered as its consumer. The decision did not create that drift, but it added a consumer, promoted the unresolved path to a boot precondition, and published the literal on two site pages. `TesseraqlRuntime.java:570` becomes `WorkHome.resolve(appHome, manifest.config()).resolve("tmp/tesseraql")`, which repairs the temp store's own drift in the same line. The published pages describe the location relative to the work directory; they stop printing `work/tmp/tesseraql/uploads` as a literal a relocation key is supposed to move.

**Preparation means writable, not present.** `Files.createDirectories` on an existing `chmod 555` leaf returns normally on JDK 25, and `Files.createFile` inside it then throws `AccessDeniedException`; for a missing leaf under an unwritable parent the exception names neither `uploads` nor the subsystem. Nothing in the tree registers a `failureHandler`, and `HttpBodyLimit` owns only 413, so an upload failing at request time reaches vertx-web's else branch as the bare 500 the boot comment claims to have removed. So the boot creates the directory and then creates and deletes a probe file in it; a failure of either is a boot refusal carrying an error code and naming the directory and the fact that it is the request-body spool. Without the probe the guarantee is empty in exactly the case that produces it — a work tree left root-owned by one `--user root` run, or a host bind mount over the volume.

**Two consequences belong on the record rather than in a reader's surprise.** Under `tesseraql host` a member's boot failure closes every already-started member and aborts the stack, so an unwritable work tree takes down sign-in and every other member, not just the member that owns it; and the escalation is new for `store: db` and `store: blob`, which created that tree lazily or not at all before. Under `--stack`, the stack surface runtime's home is materialized outside the declared volume, so its spool is writable but unswept; members spool inside the volume.

**Accepted costs, said out loud.** Boot creation removes the per-request `mkdirsBlocking` but not the per-request `existsBlocking` stat, so every url-encoded and multipart POST still stats the spool directory from the event loop — one stat on a local directory, and the reason the uploads subtree must stay node-local even where the `file` temp store points at shared storage. A part orphaned by a kill is removed by nobody: `setDeleteUploadedFilesOnEnd(true)` covers the exchange, not the process. And the installer walks a member's whole tree with no exclusion when hashing package identity, so an orphaned part inside `work/` can make an idempotent re-install of an identical package refuse; that is pre-existing — the temp store, the draft store and the audit trail already write into that tree — and if it is ever fixed the fix is an installer decision, not an edge one.

One claim of the original decision is dropped: the `HttpEdgeSettings` record does not stop later slices from colliding. It exists because named, documented components beat a growing positional parameter list, and a slice that adds a component still edits the record header and the single construction site.

## Decision 8 — A connection that stops taking bytes is reclaimed at the transport

**What is true today.** `RouteEdge` and `AssetRoutes` each write a response one 64 KB chunk at a time and wait for the previous chunk before reading the next (RouteEdge.java:514-537, `written.get()` at :530; AssetRoutes.java:363-392, `written.get()` at :384). That wait is the backpressure, and it is unbounded: `written.get()` has no deadline, so a peer that reads the response head and then stops reading parks a virtual thread for as long as it likes. For a route it parks more than a thread — `HttpAdmission` releases its permit from the routing context's end handler (HttpAdmission.java:86) and `RouteEdge.stream` reaches `response.end()` only after the write loop finishes, so one of forty default permits is held for the life of that TCP connection. Forty stalled sockets close the runtime to everyone else.

**The obvious fix is the wrong one, and the campaign proposed it.** Bounding the per-chunk wait and aborting the way the mid-body catch already does frees the thread and does **not** free the permit, because that close cannot happen. Vert.x's connection close is a graceful shutdown that flushes an empty buffer and closes the channel only once that flush completes; the empty buffer queues behind the stalled chunk, so the channel is never closed, no end, exception or close handler fires, and the permit is leaked rather than released. Measured: with a two-second per-chunk bound against a socket whose receive buffer was filled and never drained, the loop exited on chunk 17 and ten seconds later the connection close handler, the response close handler and the response end handler had all still not fired, with the socket open. The campaign's own headline — "stops holding a thread and a permit" — and its test — "polls until it answers 200 (the permit came back)" — are both false on the code it prescribed.

**The connection idle timeout is the instrument.** `setIdleTimeout` installs Netty's `IdleStateHandler` on the server pipeline, and Vert.x answers the idle event by closing the channel directly, skipping the graceful close an application cannot get past. Measured against the same stalled peer, with today's bare `written.get()` and no per-chunk bound at all: the write future failed, the loop left after three seconds, and both the response and connection close handlers fired. One setting reclaims the thread, the permit and the socket; the per-chunk bound reclaims the thread and leaks the other two.

**What changes.** The runtime declares `tesseraql.http.idleTimeoutSeconds`, defaulting to 300, with `-1` as the visible opt-out — the spelling `maxBodyBytes` already uses, because `threadCount` refuses anything below 1 and cannot read a zero. It rides `HttpEdgeSettings` and is applied at both server sites: `TesseraqlHttpServer.java:87` for a runtime's own port and `StackRelay.frontOptions` (StackRelay.java:79-81) for the front door, so that under `tesseraql host` the browser's connection is bounded and not only the member's.

**Neither write loop gains a deadline.** Once the idle bound is in place the per-chunk bound's residual coverage is empty — `IdleStateHandler` runs its clock from the last *completed* write, so a peer trickling slowly enough to stall a chunk is cut anyway — and it costs two things worth avoiding. Its clock spans the `runOnContext` handover, not the write, so on the one Vert.x every runtime in a stack shares it can fire on a healthy download behind a momentarily busy event loop. And on the asset side it has nowhere to land: `AssetRoutes.stream` has no catch around its write loop, so the throw would skip the short-delivery branch that knows how to abandon an announced `Content-Length` and reach `fromStorage`'s `catch (IOException) { notFound(...) }`, which is guarded on `!gone.get()` and would silently do nothing — a permanently hung client with no log line and no close. Assets take no admission permit in any case, so the asset half of a per-chunk bound would release only the thread this design has already called cheap.

One stated reason for the campaign's *offered* idle timeout was also measured false: a buffered `end(buffer)` to a stalled peer fires the end handler about ten microseconds later, because the response's write-with-end path calls the end handler synchronously — a buffered response releases its permit at the `end()` call, not when the bytes leave.

**Accepted costs, said out loud.** The bound is all-idle, not write-only, so it also cuts a connection whose route has read its request and written nothing for the interval. 300 seconds clears every silent interval the runtime declares with a wide margin — a statement is bounded at 30 by default, a live stream heartbeats every 25, and Studio's copilot bounds each model call at 60. The number is deliberately five times the largest of them rather than twice: the cost of being too generous is a stalled socket held longer, while the cost of being too tight is cutting somebody's legitimately long report, and only one of those two is a correctness failure. An application that deliberately removes its statement bound raises this key or sets `-1`. Neither bound stops a peer that trickles fast enough to keep writes completing; at 64 KB per interval a client holds a permit for roughly 3.5 kbit/s, and a whole-response deadline is a separate question this decision does not claim to answer. The idle close is anonymous: it does not name the route in a WARN the way a per-chunk catch would have, which is the price of not shipping the asset landing-site hazard. And a stalled socket still survives up to the full interval, where a per-chunk bound of 60 would have freed the thread sooner — the thread was the cheap resource here, and freeing it early while leaking the permit and the socket is the trade the original decision made by accident.

## Decision 9 — A page number is bounded, and the bound is published

**What is true today.** `?page=` is a framework-owned parameter, parsed in one place — `PageBinder.positiveLong` (PageBinder.java:184-198) — which refuses only values below 1. Everything above that flows into three products: the offset leg's `(number - 1) * (long) size` (PageBinder.java:76) and the snapshot leg's two slice bounds (:133-135), which `ViewBinding` repeats from the `snapshot` map the binder published.

The blast radius the campaign recorded is wrong, and the correction matters for how the change is announced. For most large values the answer is an empty 200: at the default size 20, `?page=3000000000` binds offset 59,999,999,980, a legal positive `long` the database answers with no rows. Only near `Long.MAX_VALUE`, and only at an even declared size, does a product wrap negative — a refused OFFSET on the offset leg (`TQL-SQL-2500`, 500) or an `IndexOutOfBoundsException` out of `subList` on the snapshot leg (`TQL-ROUTE-5000`, 500). At an odd size the same input answers 200. The dominant transition this change makes is 200 → 400, not 500 → 400.

The published contract says nothing about any of it: `OpenApiGenerator` emits `page` as `{type: integer, minimum: 1, default: 1}` (OpenApiGenerator.java:113-118) while the `size` parameter three lines below publishes its `maximum` (:120-126).

**What changes.** `PageBinder` bounds `page` at `Integer.MAX_VALUE` and refuses anything above it through the existing reject path — `TQL-FIELD-2001`, rendered 400 by the arm already there (ErrorResponseRenderer.java:552), no new switch arm and no status-ledger row. The ceiling is flat rather than derived from the declared size: with `number <= Integer.MAX_VALUE` and `size` an `int`, the largest product any expression can form is 4,611,686,011,984,936,962, comfortably inside `long`, so one constant removes the overflow from every site at once instead of a divisor re-derived per route. The constant lives in `tesseraql-yaml` beside `PageSpec`, which is also where `OpenApiGenerator` lives, so both read the same number and the generator publishes it as the `page` schema's `maximum`. A framework-owned parameter whose refusal exists only in code is a contract the generator lies about, and `openapi.json` is a shipped artifact.

The `?size=` call site is left exactly as it stands, and the asymmetry is chosen rather than inherited. `size` is read only when the author declared `maxSize`, and is then clamped by `Math.min` against that declared ceiling (PageBinder.java:175-182) — a ceiling the contract already publishes. `page` has no author-declared ceiling to clamp against, so it is refused, which is what the pagination contract already promises for a bad value. The refusal adds no new message literal: it throws through the unchanged `reject(name, raw)`, because `ErrorIndex` joins at most two meanings per code and `TQL-FIELD-2001`'s cell is already at that cap with an ellipsis — a bespoke sentence would displace a published one and turn `GeneratedReferenceTest` red on a change that otherwise regenerates nothing.

**The same overflow outside the binder is closed here or the CHANGELOG lies.** `PageBinder` runs only where a route declares `pagination:`, and no Studio route declares one. The audit trail parses `page` itself (`Math.max(1, Integer.parseInt(...))`) and slices in `int` arithmetic at `AuditTrail.java:85-86`, where `(p - 1) * 50` wraps negative from page 42,949,674 upward — at `?page=2147483647` the window is `subList(-100, -50)`, which throws for any log size including an empty one, uncaught, rendered as `TQL-ROUTE-5000` / 500. That arithmetic widens to `long` here, as does the data browser's `int offset = safePage * PAGE_SIZE`, whose overflow reaches `setMaxRows` with a negative row count and degrades to an in-page banner. The first detonating page is 42,949,674, independent of whichever ceiling is chosen, so this is a scope obligation rather than a reason to move the bound. Both are two-line changes.

**Accepted costs, said out loud.** Cost inversion: after the fix `?page=2147483647` is *admitted* and binds `limit 21 offset 42949672920` while holding an admission permit for the whole ordered scan, where today it fails at the executor. The capability is unchanged — the same cost is already purchasable with `?page=1000000` — so what moves is only which value is cheapest to send; bounding scan depth is a separate decision. The `page`/`size` asymmetry is stated as a choice, not an oversight: two answers to "out of range" on two framework-owned parameters, because their ceilings have different owners. The pagination renderers can emit a `page=2147483648` link at the ceiling that the new bound would refuse; it is left unclamped and recorded in the constant's Javadoc, because the offset leg needs a real row at offset 42,949,672,920 and the snapshot leg's `hasNext` is measured against a membership capped at 500, so no result set can reach it. And an `openapi.json` that now publishes `maximum` on `page` breaks byte-equality with every operator's kept baseline and moves `openapiSha256` in release evidence — the alternative is a published contract that disagrees with the runtime.

## Decision 10 — A malformed request body at an authentication endpoint is the caller's fault

**What is true today.** `LoginRoutes.parseBody` ends in a bare `mapper.readValue(raw, Map.class)` (LoginRoutes.java:436). A body that is not parseable JSON leaves a `JsonProcessingException` for the pipeline's catch-all arm, where `ErrorResponseRenderer` finds no `TqlException` and answers `TQL-ROUTE-5000` at 500. Eleven endpoints share that helper through its callers: login, logout, the three session endpoints behind `requireSessionAndCsrf`, token exchange, and the three recovery legs. A body of the literal `null` parses to a null map, which the existing `raw == null || raw.isBlank()` guard (LoginRoutes.java:433) does not cover, and the first `body.get(...)` NPEs into the same 500. Both are a caller's mistake reported as the server's, and both land in the 5xx outcome class the runtime measures itself by.

**What changes.** `parseBody` null-guards the parsed map and catches `JsonProcessingException`, raising the shared `TQL-FIELD-2002` — the code the declarative surface already raises for the same fault (RequestBinder.java:31, :257-262). The renderer answers it at 400 with no new switch arm and no status-ledger row, because 2002 falls outside the ledger's LD-or-4000-4999 scope. No authentication-specific SEC code is minted: the SEC arm ends in `default -> 500` and SEC-4xxx is inside the ledger's scope, so a new code there costs an explicit arm and a ledger review for a fault that is not about authentication at all.

The repository does hold a second answer for this same fault — `OperationsRoutes` mints `TQL-BATCH-4043` for an unparseable job-run body — and that is recorded here so it is not re-litigated as an oversight: a job-run body is a BATCH concern with a BATCH domain to name it, while the authentication endpoints have no domain of their own for a malformed request shape.

**Three details of the raise are load-bearing, and getting any of them wrong ships a worse page than the 500 being replaced.**

First, the sentence reaches the caller through `details.message`, not through the exception's message. `ErrorResponseRenderer` overwrites the envelope's message with the localized status phrase (`error.put("message", statusMessage(tag, status))`, :131) and no catalog defines `tql.http.400`, so a message-only throw answers exactly `{"error":{"code":"TQL-FIELD-2002","message":"Bad Request"}}` and, for an `HX-Request`, an alert whose title is "Bad Request" and whose body is empty. The refusal is therefore built with `.message(sentence).details(Map.of("message", sentence))`, the shape the import commit refusal established; `details.message` survives the renderer verbatim into the JSON envelope and into the alert body. `RequestBinder`'s raise is reshaped the same way in the same change, so the two doors answer alike in substance and not only in status.

Second, the sentence is "The request body must be a JSON object", at both sites. "Request body is not valid JSON" is false for `[]`, `123` and `"abc"` — all valid JSON, refused because they are not objects — and `[]` is one of the cases this change tests. The wording is shared verbatim so `ErrorIndex` dedupes it: the meaning column joins at most two distinct meanings and hides the rest behind an ellipsis (ErrorIndex.java:604-616), and FIELD-2002 already carries two. A third, differently worded sentence evicts the mass-assignment meaning from the published page while `GeneratedReferenceTest` stays green.

Third, the new constant carries no Javadoc, and the sentence is an inline literal in the throw statement. `ErrorIndex` tries the declaration statement's own literals, then the Javadoc directly above it, and only then a use-site message. A declaration in `LoginRoutes`' house style — a `/** TQL-…: … */` above the constant — is picked up as a third meaning and evicts a published one. Equally, the sentence must not be hoisted into a local variable before the throw: `TQL-LD-2867` is published as "token mismatch" — the constant's name read as prose — precisely because its raise site assigns its message to a variable first. The constant is declared in `RequestBinder.java:31`'s exact shape.

**Accepted costs, said out loud.** Two codes now answer "the request body is not a JSON object": FIELD-2002 and the shipped, mapped, job-scoped BATCH-4043; retiring the second is a separate change on the operations surface, not a rider here. The published meaning of FIELD-2002 stays capped at two sentences, so the code's third raise reason — "Unknown input field" — remains unpublished, as it is today. `ScimRoutes` and `McpRoutes` carry the same defect in a worse form — they pass the body straight to `readValue` with no null guard, and `readValue((String) null, …)` throws `IllegalArgumentException`, which this catch would not cover; that is recorded as a lead so the next reader does not assume the JSON-body surface was swept. The refusal becomes swappable where the 500 was not, deliberately: at 400 the renderer emits the field-errors fragment and the bootstrap's 4xx allowance opens for it, and with `details.message` the swapped alert reads the reason in its body. And the `SHARED` sentence in `ErrorCodeUniquenessTest` is unguarded prose — no assertion reads it — so the forcing function for a reader is the regenerated reference page; the sentence is already stale on main, and the pull request says so.

## Decision 11 — A capacity refusal answers the caller it has, and the swap allowance stays 4xx

**What is true today.** The framework bootstrap swaps an htmx response only when its status is a 4xx and its body carries one of the declared fragment markers. The status test comes first and returns before the body is read at all (tesseraql.js:117-120, with the body read only at :121), which is the rule already published: "5xx keeps htmx's default handling" (docs/hypermedia-ui.md:99). A 503 therefore has no swappable body — not because it lacks a marker, but because it never reaches the marker scan. Minting a fragment for a capacity refusal, as the campaign proposed, would produce markup no shipped client renders.

**That rule stays.** Widening the allowance to 5xx would break two shipped contracts. An async job card stops polling by having no trigger, so swapping a capacity alert into it would end the poll permanently while the import kept running; today's no-swap leaves the card alone and the next two-second poll recovers. And the allowance's first branch clears `isError` (tesseraql.js:127), which the kit's unsaved-changes guard reads as its cue to re-baseline a form — a refused save would leave the user's unsent work looking saved. An in-page "the runtime is busy" alert is an alert with no field to attach to and no contract above it to belong to; that is a kit behaviour on `htmx:responseError` and belongs upstream in Hypermedia Components, never patched in TesseraQL.

**The stream refusals have no renderable surface by construction.** Every SSE mount in the product is consumed by an `EventSource`: the shell's inbox bell, every `refreshOn:` region on the list, detail and dashboard templates, and the Studio copilot. `EventSource` exposes neither the status nor the body of a failed connect to page code; the htmx extension's whole error surface is an untyped error followed by a reconnect. Decision 3's path discriminator guarantees that the only caller who can be refused with `TQL-RATE-4296` is one that cannot read the refusal. `SseRoutes` already records the right answer for this shape (SseRoutes.java:126-147): the refusal is a JSON envelope for an API client, the reconnect is the browser contract, and a refused live badge degrades to what docs/realtime.md already promises. `TQL-RATE-4295` and `TQL-RATE-4296` are out of scope for any rendering question.

**What the campaign had not answered, and this decision does.** The surface where a 503 is not an htmx response at all. The admission gate exempts only health and assets (HttpAdmission.java:75); a top-level navigation and the snapshot pager's native form POST (list.html:69, :137-152) both take a permit, and both are refused with a bare JSON envelope written straight to the wire (HttpAdmission.java:96-105; the front door does the same at StackRelay.java:737-748). The browser paints `{"error":{"code":"TQL-RATE-4293",…}}` as the whole document, and a user paging a frozen snapshot loses up to five hundred membership tokens with it.

So the gate and the relay negotiate on `Accept`. When the caller asks for `text/html`, a capacity refusal answers a self-contained constant HTML body — a busy sentence and the code — instead of the envelope; every other caller keeps the JSON envelope unchanged, and an htmx request keeps today's no-swap. The body is a fixed string written on the event loop, the same cost the gate already pays: no template engine, no route, no worker. It is English by construction, for the reason HttpBodyLimit already records for the 413 — a pre-route handler has neither a negotiated locale nor a route to read one from.

**The app's own error template is deliberately not consulted.** That contract belongs to `ErrorResponseRenderer`, which holds the app home and renders per-app pages for route failures; the gate and the relay run ahead of any route and hold neither. Rendering an app template inside the handler that exists to shed load would spend, on the refusal path, exactly the work the refusal exists to avoid. The same exclusion covers the 413 that `HttpBodyLimit` writes: router-level and relay-level refusals answer with the runtime's own constant body, never the app's error page. That is one recorded rule, not three silent ones.

**Accepted costs, said out loud.** An htmx-issued request that meets the gate still shows the user nothing — htmx does not swap a 5xx, and the kit's network-retry behaviour listens only for send errors and timeouts, and its after-request clear wipes a standing retry banner when the retry itself is refused. The design doc records that symptom as "the page is left unchanged and any standing network-retry alert is cleared" rather than working around it here. A refused stream reconnects at roughly one attempt per 1.25 s: the SSE extension's backoff is `Math.random() * (2 ^ retryCount) * 500` — XOR, so the capped steady state is a uniform [0, 2500) ms delay — and the `Retry-After: 5` the refusal sends is read by nothing in that extension; the header stays correct for API clients, and the code comment says no shipped browser client reads it. And the constant HTML body is English on every localized page, because giving the gate a locale means giving it the message catalog and a render, which is the work the refusal exists to avoid.

## Decision 12 — The transport defaults this edge relies on are written down, and the files allowed to declare them are pinned

**What is true today.** The framework declares nothing about its server socket. `TesseraqlHttpServer.start()` builds the server with `vertx.createHttpServer(new HttpServerOptions())` (TesseraqlHttpServer.java:87), and the gateway's front door sets two fields and inherits the rest (`StackRelay.frontOptions`, StackRelay.java:79-81). Every bound the decisions above are about — 256 form fields, an 8192-byte form attribute, 1024 buffered bytes, an idle timeout of 0 — is Vert.x's, borrowed and unrecorded. This is the defect class the edge already names out loud: "the transport upgrade to Vert.x 5 changed that default from unlimited to 10 MB, silently — a borrowed bound nothing declared."

**A ledger that diffs the framework's options against `new HttpServerOptions()` does not close that class, and the campaign's proposal is struck.** The diff is empty in exactly the state the bug lives in: on today's tree it compares a default object against a default object and reports nothing while 8192/256/1024 are live; after this campaign it would record three fields and stay silent about the other seventy. It is also not writable as described — measured on 5.1.6, five getters return nested configuration objects with no `equals`, so two freshly constructed defaults already differ on compression, the HTTP/1 and HTTP/2 configs, transport options and WebSocket config, and reading the ALPN versions lazily creates the SSL options on the receiver, so a reflective sweep poisons its own comparison and answers differently depending on iteration order. Keeping it green would need a hand-maintained exclusion list, which is the maintenance the proposal claimed to remove. And the cited precedent is misstated: all seven ledgers in tesseraql-docs-reference walk main sources, grep source *text* for a construction token and assert a set of *file paths* (HttpClientLedgerTest.java:59-86); none reads a value, and none could reach `TesseraqlHttpServer`, which is package-private and would have to widen immediately before the API freeze.

**What changes: two pieces, each in the idiom that already fits it.**

A construction-site ledger, in the family. `HttpServerOptionsLedgerTest` greps every main source for `new HttpServerOptions(` and asserts the set is exactly `TesseraqlHttpServer.java` and `StackRelay.java`. Pinning the constants is what makes the guard fire at the only moment it can. Dependabot bumps Maven libraries weekly and individually, so a Vert.x release that moves a default the design leans on arrives as its own pull request; a test naming that constant goes red there, where a diff computed on the new version's defaults would stay green. Reading back the declared values is what makes the record honest: `setIdleTimeout` at decision 8's number is invisible to any delta while `DEFAULT_IDLE_TIMEOUT` is 0.

**Accepted costs, said out loud.** The file-path ledger cannot detect a wrong *value* — it only pins which files may build a server's options; value coverage is the pinned-defaults test's job, and splitting the two is what keeps the ledger in the idiom the repository already maintains. The pinned list is hand-curated and covers eleven constants, not all seventy-three settings `HttpServerOptions` carries; an exhaustive verdict map over the options' JSON was considered and rejected — it is deterministic, but it commits the repository to re-adjudicating every Vert.x settings addition, and fourteen getters have no JSON key at all, so even the exhaustive form would carry a blind spot at far greater cost. `BodyHandler` and the gateway's `PoolOptions` are covered by constant-pinning and construction-site discipline only, because `BodyHandler` exposes five defaults and zero getters — a configured handler can never be read back by any mechanism. And the gateway's front door still inherits most transport settings: under the shipped image the socket a client connects to is that front door, not a member's server, so decision 5's form bounds are declared on a server that in that deployment shape never terminates a client connection. This decision records that gap and pins its construction site; it does not close it.

## What the refutation review replaced

The campaign plan was reviewed before any of it was written, by readers whose instruction was to
refute rather than to improve. Nine positions did not survive. They are listed here with the
measurement that replaced them, because a design document that quietly drops a reason teaches the
next reader nothing.

| The plan said | Measured | Now |
| --- | --- | --- |
| An exempt SSE path is "an unbounded door for an anonymous caller" | `BrowserAuthenticator` refuses an unauthenticated connection before the stream opens | The reason is the bound on connection *attempts*, each costing a virtual thread and a session read before any registry cap |
| An exemption is unbounded across subjects — 256 x 4 = 1024 streams | `LiveStreams.total` is one global counter refused at `maxTotal`; the per-subject path evicts | The arithmetic is impossible and is struck |
| `maxEventStreams` defaults to `live.maxTotal`, making `TQL-RATE-5030` reachable | An outer gate equal to the inner cap refuses first; the registry is built only when a route declares `emit:`, and its key is parsed with a bare `Integer::parseInt` | Defaults to the same number `maxInFlight` does, read through the same validation |
| The gateway discriminates streams by `Accept: text/event-stream` | The repository's own MCP client sends that header on synchronous tool calls; a header is the caller's to set | Path classification against the member's own base path |
| `maxStreamsPerMember` defaults to 256 | A member admits forty in flight, so 216 of 256 forwards would be refused one hop later | `maxConcurrentPerMember x 4` |
| Raising only two of the three form bounds "would leave the textarea broken on a real network" | A 5,000,000-byte field in 610 flushed 8 KB chunks returned 200 with the correct digest, both encodings, buffered bound untouched | `maxFormBufferedBytes` is not touched |
| Set the form ceilings to `maxBodyBytes`, or to `-1` | Equal bounds are a race the decoder wins (400 where 413 is promised); `-1` removes the decoder's only self-termination (71 MB retained, decoder alive) and leaves a 100 MB post unanswered under the body-limit opt-out | `maxBodyBytes + 65536`, clamped, with a declared 10 MB under the opt-out |
| `maxFormFields` defaults to 1000, above `PageSpec.effectiveCap()`'s 500 | A list form posts `cap + min(size, cap) + chrome`; the legal `{cap: 500, size: 500}` posts 1002 | 10,000, plus a build-time inequality over the framework's own defaults |
| Bound the per-chunk wait with `tesseraql.http.writeStallSeconds` | The loop exits, but ten seconds later no close, end or exception handler has fired and the socket is open — it frees the thread and leaks the permit and the socket | `tesseraql.http.idleTimeoutSeconds`, measured to reclaim all three |
| Mint `TQL-SEC-4151` and add `case 4151 -> 400` | SEC ends `default -> 500` inside `StatusMappingLedgerTest`'s scope; FIELD already answers 400 | `TQL-FIELD-2012`, and this campaign makes no edit to `ErrorResponseRenderer` at all |
| Diff the framework's `HttpServerOptions` against a default one | Empty in the state the bug lives in; five getters return nested objects with no `equals`, and reading the ALPN versions mutates the receiver | A construction-site ledger plus a pinned-constants test |

## Deliberately not in this design

**The swap allowance is not widened to 5xx.** Decision 11 records why: an async job card stops
polling by having no trigger, and the allowance's first branch clears `isError`, which the kit's
unsaved-changes guard reads as its cue to re-baseline a form. An in-page "the runtime is busy"
alert is a Hypermedia Components behaviour on `htmx:responseError` and belongs upstream.

**No per-chunk write bound.** Decision 8 measured it as an instrument that frees the cheap
resource and leaks the two expensive ones.

**No boot-time or lint-time coupling between a route's pagination cap and the transport's field
count.** Decision 5 records all three mechanisms that were considered and why each is
unimplementable or disproportionate; a build-time inequality over the framework's own defaults is
what holds the relationship instead.

**`deploy/Dockerfile` is not edited.** Its working directory stays root-owned. The boot-time
writability probe in slice 3 is what catches the class now, at boot, naming the directory and the
subsystem — which is a better detector than a form post that fails at request time.

## Recorded gaps — known, not closed

- **A forward inside the origin fence takes no per-member permit**, before or after this campaign:
  `StackRelay` returns ahead of the permit block for it. A stream served by the stack surface
  runtime is therefore unbounded at the front door. Closing it changes which runtime serves the
  stack surface and is a larger question than a bound.
- **The gateway's front door inherits most transport settings.** Under the shipped image the
  socket a client connects to is the front door, not a member's server, so decision 4's and
  decision 5's form bounds are declared on a server that in that shape never terminates a client
  connection. Decision 12 pins its construction site; it does not close this.
- **A subscription outlives its connection by up to one heartbeat.** The admission permit returns
  when the routing context ends while the registry slot is released only when the producer's next
  await returns. After decision 2 that no longer decides which gate refuses.
- **`ScimRoutes` and `McpRoutes` carry decision 10's defect in a worse form** — the body reaches
  `readValue` with no null guard, and `readValue((String) null, …)` throws
  `IllegalArgumentException`, which decision 10's catch does not cover. Recorded so the next
  reader does not assume the JSON-body surface was swept.
- **`TQL-BATCH-4043` and `TQL-FIELD-2002` both answer "the request body is not a JSON object."**
  A job-run body is a BATCH concern with a BATCH domain to name it; the authentication endpoints
  have no domain of their own for a malformed request shape. Recorded as settled, not overlooked.
- **The import surface delivers a field-errors fragment into `hx-select=#<formId>-result`** while
  a bare alert carries no such id, so htmx selects nothing. Pre-existing on the shipped 413, and
  a Hypermedia Components or template concern either way.
